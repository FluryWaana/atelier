# Parcours de projet Rust — candidat R05

Le projet enregistre une commande de vérification, une branche cible, l’autorisation des parcours et l’option de correction P0/P1 (deux cycles maximum). Leur modification utilise les mêmes préconditions de concurrence que les autres réglages ; les options booléennes ont des préconditions typées. L’enregistrement ne lance rien.

Depuis une tâche avec worktree prêt, une confirmation lie le besoin, le profil public et le projet affichés. Le parcours persiste son identifiant, ses étapes et les références aux runs. Le superviseur commun enchaîne développement puis vérification. Chaque lancement est réservé avant sa préparation ; un arrêt accepté entre réservation et démarrage rend ce lancement inutilisable. Les agents gardent leurs interactions, journaux bornés et arrêt des descendants existants.

Après vérification réussie, le parcours attend le contrôle explicite du commit, du push et de la PR/MR dans les panneaux existants. Il ne rejoue aucune publication. Après confirmation d’une PR/MR liée aux branches attendues, il revérifie les sources puis lance la review. Son résultat est revalidé contre les commits source/cible/base et le besoin actuels ; les sources doivent encore correspondre à la vérification. Les constats P0/P1 peuvent déclencher deux corrections au maximum, chacune suivie de vérifications et d’un nouveau contrôle de publication. Les autres résultats restent prêts pour contrôle humain ou bloqués lorsque les critères ne sont pas couverts. Aucun critère humain n’est coché automatiquement.

Un redémarrage interrompt les parcours actifs sans nouveau lancement. La reprise est explicite et refuse un besoin, un profil, un projet ou un worktree changé. Une étape de publication/review interrompue reprend par les vérifications. Les opérations incompatibles sur la tâche, les projets, les profils, les sauvegardes ou les mises à jour sont bloquées pendant l’activité. L’arrêt du parcours reste disponible via une route d’annulation exacte. Les données restaurées restent interrompues et leurs reviews/vérifications périmées.

Les exécutions typées de commit/push/publication sont extraites de leurs handlers pour partager leurs réservations et récupérations existantes. Scénarios Git écrits, **non compilés/non exécutés**. ## Enchaînement de publication candidat

Après le commit explicite, le panneau permet d’approuver l’aperçu de push ou de PR/MR préparé dans les composants existants. L’autorisation fige site, révision des identifiants, dépôt, branche, commits, cible et contenu. La création d’une branche absente exige une seconde autorisation liée au même instantané. Toute modification d’un brouillon invalide ces autorisations, même si le texte d’origine est ensuite rétabli. Un aperçu déjà persisté est distingué des modifications de formulaire plus récentes.

Le parcours revérifie les sources avant l’envoi, relit l’aperçu distant et réutilise les intentions de push/PR existantes. Il pousse avec bail explicite, crée une PR/MR brouillon si nécessaire, relit le résultat puis lance la review sur les commits observés. Pour une PR/MR existante, ses branches, commits, état et identité sont recontrôlés avant l’envoi. Seul le changement source approuvé est accepté lors de la relecture après push ; un autre changement suspend le parcours. Les modifications humaines, l’index et FETCH_HEAD restent conservés.

Après un arrêt ou redémarrage, aucune étape de publication approuvée n’est rejouée. Les intentions distantes incertaines doivent être rapprochées dans leurs panneaux ; la reprise refait les vérifications et demande une nouvelle approbation. Scénarios de stockage, refus d’une PR/MR modifiée et invalidation des deux autorisations dans WebDriver écrits seulement. La fixture d’approbation ne possède ni profil exécutable ni vrai worktree et n’est jamais envoyée : elle ne prouve aucune vérification, aucun push ni création distante. **Aucun scénario exécuté, aucun résultat de qualification nouveau.**

## Commit dans le parcours candidat

Le panneau de commit propose aussi d’intégrer son aperçu confirmé au parcours en attente. Auteur, message, chemins, parent et arbre Git sont réservés dans le parcours avant lancement. L’exécution réutilise le commit avec index privé et déplacement conditionnel de branche existant. Seul le commit attendu réellement observé permet d’avancer ; une observation différente ou incertaine suspend le parcours. Les vérifications sont ensuite refaites, sans conserver un ancien résultat comme preuve du nouveau commit. L’approbation de publication reste distincte.

Après redémarrage, le commit n’est jamais recréé automatiquement. Il faut rapprocher une éventuelle intention incertaine, puis reprendre les vérifications. Le formulaire efface uniquement les champs exacts d’un aperçu envoyé par ce panneau lorsque son effet confirmé arrive ; les autres brouillons restent conservés. Scénario de stockage écrit avec résultats injectés explicitement fictifs. Scénario WebDriver étendu pour un fichier créé uniquement dans le worktree synthétique marqué, commit natif prévu, index comparé octet pour octet, source conservée et commande synthétique vérifiée après commit. **Écrit uniquement, non compilé/non exécuté ; aucune nouvelle preuve native ou navigateur.**

## File et parcours de projet candidats

Une entrée de file choisit explicitement une exécution simple ou le parcours de son projet. Dans le second cas, création/reprise du parcours et réservation de l’entrée sont enregistrées dans la même transaction SQLite. La file conserve l’identifiant exact du parcours ; elle attend ses validations de commit/publication, puis avance seulement sur son état prêt pour contrôle humain. Une erreur, un blocage, une annulation ou une interruption remet la file en pause. Le résultat des critères humains n’est jamais changé par ce mécanisme.

Après redémarrage, la file reste en pause et conserve ses liaisons. Sa reprise peut reprendre les étapes locales interrompues explicitement autorisées, sans rejouer commit ou publication. Un parcours déjà terminé est retiré sans nouvel agent ; un parcours remplacé par une autre opération exige retrait/réajout de l’entrée. Une nouvelle entrée après achèvement autorise un nouveau parcours distinct. L’interruption des données restaurées précède la récupération de la file afin qu’une ancienne review prête ne fasse pas avancer la file restaurée.

Le panneau montre le mode des entrées et rappelle les reprises locales autorisées. Une tâche interrompue peut aussi démarrer explicitement un nouveau parcours avec ses réglages actuels lorsque la reprise du précédent est refusée ; les fichiers et effets incertains restent protégés. Les pauses répétées identiques n’écrivent plus une révision SQLite à chaque passage du superviseur.

Scénarios de stockage écrits : coexistence tâche/parcours, attente sans agent supplémentaire, récupération, même identité à la reprise, retrait d’un parcours prêt sans rejeu, nouvelle identité après nouvelle autorisation et rollback intégral d’une création si l’écriture de réservation échoue. États prêts/attente injectés dans ces tests sont des fixtures, pas des preuves d’exécution d’agent. WebDriver étendu pour attacher le parcours synthétique en attente à la file, vérifier l’absence de nouveau run, arrêter puis retirer l’entrée. **Tous non compilés/non exécutés.**
