# M04 — Git, fichiers, processus et agents

## Arbres de processus Windows — candidat après `41e7742`

`process_tree::ContainedChild` prépare un Job Object non héritable avec fermeture destructrice, crée le programme suspendu et sans fenêtre, l'affecte au job, puis reprend son unique thread initial. Aucun protocole de coopération du programme n'est nécessaire, contrairement à la fixture M01. L'énumération est limitée au PID du processus encore détenu ; le handle de thread est revalidé avant reprise. Un état inattendu (plusieurs threads, affectation impossible) refuse le lancement et arrête le processus suspendu. Les API stables de Rust ne donnent pas encore directement le handle du thread initial ; cette stratégie utilise les API Microsoft [CREATE_SUSPENDED](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags) et [ToolHelp](https://learn.microsoft.com/en-us/windows/win32/toolhelp/traversing-the-thread-list), sans dépendance ni API Rust nightly.

La fin naturelle arrête aussi les descendants restants. L'arrêt explicite termine le job, attend le parent et vérifie le compteur natif de processus actifs avec délai borné. L'abandon ferme le job et déclenche la terminaison OS. Aucun arrêt par PID réutilisable. Les scénarios Windows ajoutés lancent immédiatement un descendant, une variante détachée, un parent laissant un orphelin, un abandon du propriétaire et une tentative `CREATE_BREAKAWAY_FROM_JOB` qui doit recevoir `ERROR_ACCESS_DENIED`. Un processus témoin indépendant doit survivre à tous ces essais.

Preuves attendues sur Windows distant. Cette tranche ne porte pas encore les groupes POSIX, la lecture bornée simultanée des flux, l'annulation des cas d'usage ou l'arrêt gracieux des protocoles d'agents. L'arrêt natif décrit ici est forcé, comme celui des serveurs Node actuels ; aucune qualification complète de M04 revendiquée.

## Réservation des ports — candidat après `4be03dc`

`launch_ports::PortLease` garde un socket IPv4 lié à `127.0.0.1`, avec choix automatique ou port validé explicite. La libération consomme la réservation ; son abandon ferme aussi le socket. Le refus conserve le message de `lib/launch-ports.mjs`. Windows utilise `SO_EXCLUSIVEADDRUSE` avant `bind`, conformément à la [documentation Microsoft](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse), pour refuser aussi la réutilisation forcée depuis le même compte. Tokio et windows-sys sont déjà présents ; aucune nouvelle dépendance.

Les scénarios candidats Node/Rust réservent seize ports distincts, refusent un port occupé puis le réservent après libération. Rust vérifie aussi l'adresse loopback, la libération sur abandon et le refus d'un socket concurrent avec `SO_REUSEADDR`. Exécution attendue sur Windows distant. Le gestionnaire de serveurs reste à porter : cette primitive ne qualifie ni la réservation logique par carte, ni le redémarrage, ni la course entre libération du socket et écoute du programme enfant.

## Détection des manifestes — candidat après `c819fd0`

`infrastructure/launch_detection.rs` porte `lib/launch-detection.mjs` sans lancer les commandes détectées. Les lectures réutilisent `CheckedFile` et les dossiers ouverts de `cap-std`. Limites historiques : profondeur trois, 300 dossiers visités, 1 Mio par fichier, dossiers exclus, héritage npm/pnpm/yarn. Les scripts Vite/Next/Angular conservent les arguments de port ; les commandes composées perdent la détection automatique. Les profils .NET exposent noms, type et origines HTTP(S), jamais leurs variables d'environnement. Les profils invalides restent visibles et non sélectionnables.

Le tri utilise ICU4X, cantonné à `atelier-app`, pour conserver le classement linguistique de `localeCompare`, avec départage lexical des équivalents canoniques. Les caractères autorisés .NET et les espaces ECMAScript sont portés par `regex`, déjà présent transitivement ; aucun de ces adaptateurs n'entre dans core ou WASM. Versions et données ICU sont verrouillées dans Cargo.lock. L'API `Collator::try_new`/`compare_utf16` a été confrontée aux sources locales exactes de `icu_collator 2.4.0`. Le pré-tri lexical POSIX provient de [`uv__fs_scandir_sort`](https://github.com/libuv/libuv/blob/v1.x/src/unix/fs.c). Les variantes de locale et les noms de fichiers non Unicode restent à qualifier sur les systèmes ciblés ; le succès d'une locale Windows ne vaut pas preuve universelle.

`cargo xtask test-project-lifecycle-parity` compare désormais aussi onze arborescences temporaires avec le véritable scanner Node : gestionnaires, frameworks, dépendances, profils, types JSON inhabituels, ordre Unicode, limites, UTF-8 invalide et liens. Les attentes natives sont calculées par Node sur le même système, sans changer les références métier figées. Les tests Rust ordinaires vérifient les commandes exactes, profils UTF-16 et l'absence de valeurs privées. La route prototype reste limitée aux dépôts synthétiques décrits dans M03, avec test de refus des chemins externes et jonctions Windows.

Validation attendue sur GitHub Windows ; aucun test, compilation ou navigateur local. Les scénarios Linux/macOS sont préparés mais reportés à la qualification finale. M04 reste ouvert : Git/worktrees, inspection/diffs, ports/serveurs, diagnostics et exécution des agents, interactions, quotas et gestion des CLI ne sont pas qualifiés par ce scanner.
